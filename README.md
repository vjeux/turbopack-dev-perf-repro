# Turbopack dev performance reproducer

A generated Next.js App Router app (pnpm) with the shapes that make `next dev` slow on
large apps, and `tpdev`, a small Rust tool that generates the app, times per-route
compiles and analyzes the dev chunks Turbopack writes.

Tracking issue with findings and fixes: https://github.com/vjeux/next.js/issues/1

## The app

Everything under `app/`, `components/` and `packages/` is generated by
`tpdev gen --out . --next 16.5.0-canary.27` (deterministic: same flags, same files).

- 40 routes (`/`, `/r0` … `/r39`); each renders 3–8 of 24 shared client "features".
- Every feature `next/dynamic`-imports one or two of the heavy client components, and loads
  one more on demand with a plain `import()` in an event handler. The same targets are
  reachable from many routes.
- `@repro/ui`: 300 components, installed by pnpm with React peer dependencies, so module
  paths look like `node_modules/.pnpm/@repro+ui@file+packages+ui_react-dom@19.2.0_react@19.2.0__react@19.2.0/node_modules/@repro/ui/dist/c12.js`.
  Routes, features and heavy components all use it.
- Six `@repro/heavy-N` packages (about 1.2 MB each, like diagram, math or codec libraries)
  and `@repro/shared` (about 160 KB, like a schema library).
- A parallel route slot (`app/@aside`) whose page reaches the heavy targets too, and a
  `React.lazy` inside each heavy component.

`next.config.mjs` reads two environment variables:

- `TP_DIST_DIR` sets `distDir`, so runs never share a cache.
- `TP_LAZY=1` turns on `experimental.turbopackLazyDynamicImports` and
  `experimental.turbopackLazyDynamicImportsSSR`.

## Running it

```sh
pnpm install
cargo build --release --manifest-path tools/tpdev/Cargo.toml
tools/tpdev/target/release/tpdev bench --app . --dist .next-a --port 3000 --out out/a \
  --env TP_DIST_DIR=.next-a / /r0 /r1 /r2 /r3 /r4 /r5 /r6 /r7 /r8 /r9 /r10 /r11
```

`bench` removes the dist dir, starts `node node_modules/next/dist/bin/next dev`, requests
the routes in order, stops the server, then writes:

- `out/a.routes.ndjson`: per route, the time of its first request, then every script the
  HTML names fetched at once, and how much `.next/dev` grew;
- `out/a.server.log`;
- `out/a.summary.json`: the routes, the chunk composition below, and the number of server
  log lines with `conflicting effects for the same key` or
  `Two or more assets with different content were emitted to the same output path`.

Other Next.js versions: `pnpm add next@16.4.0`. A locally built `next-swc`: add
`--env NEXT_TEST_NATIVE_DIR=/path/to/dir/with/next-swc.linux-x64-gnu.node`.

### Chunk composition

`tpdev analyze --dist .next-a` parses every chunk under `.next/dev/static/chunks` and
`.next/dev/server/chunks` into module registrations
(`"[project]/<path> [<layer>] (<type>)", ((__turbopack_context__) => { … })`).

- A module is identified by its whole key, so an async loader stub is not counted as the
  module it loads.
- A module is a duplicate when its key is registered in more than one chunk file. Duplicate
  bytes are the bytes of every copy but the largest.
- Import variable bytes are the matches of `__TURBOPACK__imported__module__[A-Za-z0-9_$]+`.

`tpdev where --dist .next-a --module <substring>` lists the chunk files that register a
module, with the size of each copy.

## Results

13 routes (`/`, `/r0` … `/r11`) on a cold `.next`, one Linux machine, Node 24.

| Next.js | Sum of first-request times | Client chunks | Server chunks | Duplicate bytes (client / server) | Import variable names (client / server) |
| --- | --- | --- | --- | --- | --- |
| 16.4.0 | 93.7 s | 50.6 MB | 55.6 MB | 62.5% / 63.0% | 34.8% / 38.2% |
| 16.4.0, lazy dynamic imports | every route answers 500 | | | | |
| 16.5.0-canary.27 | 89.6 s | 51.2 MB | 56.2 MB | 62.7% / 63.4% | 35.4% / 38.9% |
| 16.5.0-canary.27, lazy dynamic imports | 89.8 s | 38.7 MB | 43.3 MB | 50.3% / 52.3% | 33.5% / 37.6% |

With lazy dynamic imports, 16.4.0 logs `[Server HMR] Update failed, re-evaluating modules:
[Error: conflicting effects for the same key …]` and every route fails with
`Two or more assets with different content were emitted to the same output path`. Canary
does not (fixed upstream by `vercel/next.js#99940`, backported to 16.4.2).

### Shorter import variable names in development

`next-swc` built from source at `16.5.0-canary.27`, without and with
[the fix](https://github.com/vjeux/next.js/pulls) (`build-native-release`), two runs each:

| | Base | With the fix |
| --- | --- | --- |
| Client chunks | 51.2 MB | 39.2 MB (−23%) |
| Server chunks | 56.2 MB | 42.9 MB (−24%) |
| Import variable names, share of bytes (client / server) | 35.4% / 38.9% | 15.6% / 19.8% |
| Average import variable name (client / server) | 298 / 323 characters | 99 / 125 characters |
| Client / server chunks with lazy dynamic imports | 38.7 / 43.3 MB | 30.1 / 33.4 MB |
| Sum of first-request times | 90.0 s, 90.5 s | 90.9 s, 90.6 s |
